# Input設計プロセス

## 1. 目的

本プロセスの目的は、LLM出力評価に使用するInput Datasetを、対象ユースケースに基づいて網羅的かつ再現可能に設計することです。

ここでいう「網羅的」とは、考え得るすべてのInputを列挙することではありません。対象ユースケースにおいて重要なInput空間を構造化し、評価目的に照らして必要な代表Inputを説明可能な形で選定できている状態を指します。

## 2. 基本方針

### 2.1 手順を標準化する

標準化の対象は、Input Datasetを設計するための手順と成果物の形式です。具体的なInput DimensionやPatternは、ユースケースごとに決定します。

### 2.2 Input設計とOutput評価を分離する

Input設計では「何を入力して評価するか」を決定します。Output評価では「出力を何に基づいて判定するか」を決定します。

両者は最終的なLLM評価で接続しますが、設計上は別の成果物として管理します。

### 2.3 網羅性と実行可能性のバランスを取る

すべてのPatternを直積で組み合わせると、ケース数が急増します。重要な組み合わせを特定した上で、評価目的・リスク・実行コストに応じて代表Inputを選定します。

---

## 3. 標準プロセス

| Step | 名称 | 主な入力 | 主な成果物 |
|---:|---|---|---|
| 1 | ユースケースを定義する | 要件、利用者、業務フロー | ユースケース定義 |
| 2 | Inputを構成する要素・条件を洗い出す | ユースケース定義、Input仕様 | Input Dimension一覧 |
| 3 | 各要素について取り得るパターンを分類する | Input Dimension一覧、実データ | Input Pattern一覧 |
| 4 | パターンの組み合わせを整理する | Input Pattern一覧 | 組み合わせ一覧 |
| 5 | 評価に必要な代表Inputを選定する | 組み合わせ一覧、評価目的、リスク | 代表Input一覧 |
| 6 | 評価用Input Datasetとして整理する | 代表Input一覧、実行仕様 | Evaluation Input Dataset |

---

## Step 1. ユースケースを定義する

### 目的

評価対象となるLLM機能の利用場面と責務を明確にし、Input設計の範囲を決めます。

### 実施内容

以下を記述します。

- 利用者または呼び出し元
- 利用する状況
- LLMへ渡されるInput
- LLMに期待する処理
- 利用目的
- 対象範囲
- 対象外
- 失敗した場合の影響

### 成果物

ユースケース定義。

### 完了条件

- 一つのユースケースとして説明できる
- Inputと期待する処理が区別されている
- 対象範囲と対象外が明示されている
- 後続工程でDimensionを検討できる具体性がある

---

## Step 2. Inputを構成する要素・条件を洗い出す

### 目的

ユースケースにおけるInput空間を、独立して変化し得る要素・条件に分解します。これらを **Input Dimension** と呼びます。

### 実施内容

ユースケース定義、Input仕様、実データ、業務ルール、既知の失敗事例などを参照し、Inputの差がLLMの出力または評価結果に影響し得る要素・条件を洗い出します。

この工程では共通のDimension一覧を機械的に適用せず、対象ユースケースから導出します。

必要に応じて、次の問いを利用します。

- Inputはどのフィールド・情報から構成されるか
- 値、形式、量、構造が変化する箇所はどこか
- 情報の有無や関係性が変化する箇所はどこか
- 実運用で発生する差異は何か
- 既知の失敗や事業上のリスクに関係する条件は何か

### 成果物

Input Dimension一覧。

| ID | Dimension | 定義 | 選定理由 | 根拠 |
|---|---|---|---|---|
| D-001 | {名称} | {何を区別する軸か} | {評価対象とする理由} | {要件・仕様・実データ等} |

### 完了条件

- 各Dimensionの意味と選定理由を説明できる
- Dimension同士の重複が整理されている
- 評価対象外とした要素を必要に応じて記録している

---

## Step 3. 各要素について取り得るパターンを分類する

### 目的

各Input Dimensionについて、評価上区別すべき状態・分類・値域を定義します。これらを **Input Pattern** と呼びます。

### 実施内容

各Dimensionの取り得る値を、LLMの挙動が同等とみなせる単位に分類します。

必要に応じて、同値分割、境界値分析、実データの分布、業務ルール、既知の失敗事例などを利用します。ただし、使用する技法や分類内容は固定しません。

各Patternには、次を記録します。

- Patternの定義
- 含まれるInputの例
- 含まれないInputの例
- 選定理由
- 優先度または重要度

### 成果物

Input Pattern一覧。

| ID | Dimension ID | Pattern | 定義 | 例 | 選定理由 | 優先度 |
|---|---|---|---|---|---|---|
| P-001 | D-001 | {名称} | {分類条件} | {例} | {理由} | {High/Medium/Low} |

### 完了条件

- 各Patternの判定条件が明確である
- 同じDimension内のPatternの重複・不足を確認している
- 実データまたは仕様との対応を説明できる

---

## Step 4. パターンの組み合わせを整理する

### 目的

複数Dimension間の関係を整理し、評価対象となるInput条件の組み合わせを定義します。

### 実施内容

Patternの組み合わせを列挙し、次を判断します。

- 実運用上、発生し得るか
- 仕様上、有効か
- 他の組み合わせと同等に扱えるか
- リスクまたは評価上の重要性があるか
- 評価対象に含めるか

全組み合わせの実行を前提にはしません。組み合わせ数が大きい場合は、デシジョンテーブル、Pairwise Testingなどを必要に応じて利用できます。

### 成果物

組み合わせ一覧。

| ID | Patternの組み合わせ | 発生可能性 | 重要度 | 採否 | 理由 |
|---|---|---|---|---|---|
| C-001 | P-001 × P-005 | {High/Medium/Low} | {High/Medium/Low} | {採用/除外/保留} | {理由} |

### 完了条件

- 採用・除外の判断理由が記録されている
- 発生しない組み合わせや重複する組み合わせを整理している
- 重要な相互作用を持つ組み合わせが含まれている

---

## Step 5. 評価に必要な代表Inputを選定する

### 目的

整理した組み合わせから、評価目的を満たす具体的なInputを選定します。

### 実施内容

各組み合わせに対応する候補Inputを用意し、以下を考慮して代表Inputを選びます。

- 評価目的との関連性
- 実運用での発生可能性
- 失敗した場合の影響
- 既知の課題や失敗事例
- 他のInputとの重複
- 評価コスト
- 再現可能性

代表Inputは、実データから抽出する方法と、条件に基づいて作成する方法のどちらでも構いません。実データを利用する場合は、個人情報・機密情報の取り扱いを別途確認します。

### 成果物

代表Input一覧。

| ID | Combination ID | Input概要 | 選定理由 | 期待する振る舞い | 優先度 |
|---|---|---|---|---|---|
| I-001 | C-001 | {概要} | {理由} | {Outputの正解ではなく、期待する挙動} | {High/Medium/Low} |

### 完了条件

- すべての代表InputをDimension・Pattern・Combinationへ追跡できる
- 各Inputの選定理由を説明できる
- 不要な重複が整理されている
- 評価目的とリスクに対して十分かをレビューしている

---

## Step 6. 評価用Input Datasetとして整理する

### 目的

代表Inputを、LLMの実行とOutput評価に利用できるデータ形式へ変換します。

### 実施内容

各レコードに、少なくとも次を保持します。

- 一意なInput ID
- ユースケースID
- Input本体
- 対応するDimension、Pattern、Combination
- 選定理由
- 期待する振る舞い
- 優先度
- データの出所
- Datasetのバージョン

LLMへ実際に渡すInputと、評価・管理用のメタデータは区別して保持します。

### 成果物

Evaluation Input Dataset。

推奨する論理構造は次のとおりです。

```json
{
  "dataset_version": "1.0.0",
  "use_case_id": "UC-001",
  "inputs": [
    {
      "input_id": "I-001",
      "input": {},
      "dimension_ids": ["D-001"],
      "pattern_ids": ["P-001"],
      "combination_id": "C-001",
      "selection_reason": "",
      "expected_behavior": "",
      "priority": "High",
      "source": ""
    }
  ]
}
```

実際のファイル形式やスキーマは、実行基盤・評価基盤に合わせて決定します。

### 完了条件

- 各レコードに一意なIDがある
- LLMへ渡すInputと管理用メタデータを区別できる
- 設計成果物とのトレーサビリティがある
- Datasetのバージョンを識別できる
- 同じ条件で再実行できる

---

## 4. 全体の完了条件

Input設計は、次の状態になった時点で完了とします。

- 対象ユースケースが明確である
- Input DimensionとPatternの選定根拠が残っている
- Patternの組み合わせについて採否を説明できる
- 代表Inputの選定理由を説明できる
- Inputからユースケースまで追跡できる
- Datasetを再利用・再実行できる
- Output評価の基準と混在していない
